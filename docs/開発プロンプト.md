# 運動ベクトル可視化アプリ 開発プロンプト

> 使い方：まず「0. 全体像」と「1. 共通仕様」を渡し、その後フェーズ1から順に1つずつ指示してください。
> 各フェーズの終わりに動作確認を挟み、前のフェーズのデータ構造を壊していないか確認してから次に進みます。

---

## 0. 全体像（最初に渡す部分）

あなたには、高校物理の授業で使う「運動のベクトル可視化アプリ」を作ってもらいます。

### このアプリが解決したい問題

高校生の多くは「速度がゼロなら加速度もゼロ」という誤概念を持っています。振り子の端、斜方投射の頂点で、速度がゼロなのに加速度が最大になることが理解できない。理論で説明しても「理解」はしても「納得」しません。

このアプリは、生徒が撮影した運動の動画から**速度ベクトルと加速度ベクトルを生徒自身に作図させ**、その向きを目で見て納得させるための道具です。

### 決定的に重要な設計思想

**答えを表示するアプリではありません。生徒に作図させるアプリです。**

自動計算した矢印を最初から表示してしまうと、生徒は「見た」で終わり「導いた」になりません。手を動かして矢印を描き、それから答え合わせをする——この順序がこの教材の本体です。実装上の便利さのために自動表示を先に出す設計にしないでください。

### 全体の流れ

```
運動を選ぶ（タイル）
  → 予測する（加速度はどっちを向く？）※ONにした場合
  → 動画をアップロード
  → 追跡して全コマの座標を得る
  → 使うコマを選ぶ（等間隔）
  → ストロボ画像を生成
  → 作図①〜⑥（手書きモード。③④は組ごとに繰り返す）
  → 答え合わせ（自動算出と予測を、軌道上のΔvに重ねる）
  →（発展）ホドグラフ
```

## 1. 共通仕様（最初に渡す部分）

### 技術制約

- **単一の HTML ファイル**。ビルド不要。
- 外部ライブラリは原則使わない。素の JavaScript + Canvas API。
- サーバー送信は一切しない。動画はブラウザ内で完結する。

**想定端末（この優先順位で最適化する）**

1. **スマートフォン** — 撮影から作図まで1台で完結できることが必須要件。撮影と解析を別端末に分けると動画の転送が挟まり、40人規模の授業が止まる。
2. **タブレット PC** — 推奨環境。画面が広く、指で描く精度も出る。撮影に使う可能性もあるため、カメラ付き端末を前提に考えること。
3. **ノート PC / Chromebook** — 動画を持ち込める場合のみ。マウス操作でも全機能が使えること。

**タッチ操作を第一とする。** 作図はすべて指で完結すること。マウス前提の UI（ホバーで出るメニュー、右クリック、細かいドラッグハンドル）は使わない。作図領域には `touch-action: none` を指定し、描画中にページがスクロールしないようにする。

**縦画面レイアウト（重要）**

**本筋の作図は、最初から最後までストロボ画像の上だけで完結します。** 別枠は使いません。390px 幅の縦画面にストロボ画像と別枠を左右に並べることはできず、上下に積めば別枠がスクロールの外に出て、始点を揃えるアニメーションが見えなくなる——という問題が、そもそも発生しない設計にしてあります。作図中はストロボ画像を画面いっぱいに使ってください。

別枠（ホドグラフ）は発展として後述しますが、そちらでも**別枠を下に置かず、同じキャンバス上で切り替えてください**。ストロボ画像がフェードして薄くなり、その場で矢印が共通の原点へ滑っていき、画面が別枠の表示に切り替わる。二枠を並べるより「同じ矢印が動いた」ことが明確になります。横画面・タブレットでも同じ演出を使ってください。

**タップ精度への対処（ルーペ）**

指先は画面を隠すため、縦画面でストロボ画像上の黒点を正確に指すのは困難です。長押しすると指の少し上に拡大表示が出て、正確な位置を確認しながら離せる仕組みを入れてください（iOS のテキスト選択にあるルーペと同じ）。実装は canvas の一部を拡大コピーして小さな円に描くだけです。**この機能の有無で、スマホでの作図が実用になるかどうかが決まります。**

**端末固有の注意点**

- **HEVC（H.265）**：iPhone のスロー撮影は HEVC で記録される。Safari では通るが、他の環境では canvas 描画に失敗することがある。読み込み時に1コマ描画テストを行い、失敗したら「この端末では再生できない形式です。撮影した端末で開いてください」と表示する。
- **回転メタデータ**：スマホの動画は回転情報を別に持つため、`drawImage` で横倒しになることがある。1コマ目を描画して縦横比を確認する処理を入れる。
- **画面の向き**：二次元運動は横画面、バネの単振動は縦画面が自然。プリセットに推奨の向きを持たせ、合っていなければ「横向きにしてください」と促す。
- **スリープ抑止**：作図中に画面が消えると作業が飛ぶ。Wake Lock API で解析中はスリープを抑止する。

### コアデータ構造（フェーズをまたいで共有する。勝手に変えない）

```js
const state = {
  video: {
    element: null,      // <video>
    width: 0,           // 元解像度
    height: 0,
    duration: 0
  },

  // フェーズ1〜2で作る。全コマ分。
  frames: [
    {
      index: 0,
      t: 0.0,           // 実タイムスタンプ（秒）。公称fpsから計算しない
      x: null,          // 追跡対象の座標（元解像度のピクセル）
      y: null,
      found: false,     // 追跡成功したか
      manual: false     // 手動打点したか
    }
  ],

  // 固定マーカー（カメラぶれ補正用）。無い場合は null
  refMarker: [ { index: 0, t: 0.0, x: 0, y: 0 } ],

  // フェーズ3で決める
  // フェーズ1で決める。追跡・背景推定より前に確定させる
  trim: {
    inIndex: 0,         // 解析に使う最初のコマ
    outIndex: null      // 最後のコマ（null なら末尾まで）
  },

  selection: {
    startIndex: 0,
    interval: 1,        // コマ間隔（フレーム数）
    count: 10           // 使うコマ数
  },

  // 生徒の作図。フェーズ4で使う
  drawing: {
    origin: null,           // 基準点 {x, y}
    positionVectors: [],    // [{dx, dy}] 基準点からの位置ベクトル
    velocityVectors: [],    // [{dx, dy}] 手書き速度ベクトル

    // 手書きΔv。deltaVVectors[k] は velocityVectors[k] と [k+1] から作られ、
    // 位置 r[k+1] に属する（③で始点を揃える点、④で置く点、⑥で重ねる点も
    // すべて r[k+1]）。インデックスを1つずらさないこと。
    deltaVVectors: [],      // [{dx, dy}]

    pairIndex: 0,           // ③④で今どの組を扱っているか（0 起点）
    prediction: null        // 予測の矢印 {dx, dy} または選択肢ID
  },

  preset: null          // 運動タイルのプリセット
};
```

**座標は必ず元解像度のまま保持してください。** 表示は縮小しても構いませんが、表示用の縮尺と解析用の座標を分離すること。ここを混ぜると後で定量計算の精度を失います。

### 座標系についての注意

画面座標は y が下向きです。物理の議論では y は上向きです。**内部処理は画面座標のまま行い、表示のときだけ変換する**か、**読み込み時に一度だけ物理座標に変換する**か、どちらかに統一してください。混在させるとベクトルの向きが場所によって上下反転します。ここは実装ミスが起きやすい箇所なので、どちらを採用したかをコード冒頭にコメントで明記すること。

## フェーズ1：動画読み込みと座標取得（手動打点のみ）

**このフェーズだけで「動画から運動の座標が取れる」道具として完成させてください。**

### やること

1. 動画ファイルをドラッグ&ドロップまたはファイル選択で読み込む。
2. `requestVideoFrameCallback` を使って動画を1回通し再生し、**各コマの実タイムスタンプを記録**する。
   - スマホの動画は「30fps」と表示されていても実際のコマ間隔は一定でないこと（可変フレームレート、VFR）が多い。**公称 fps から時刻を計算しないでください。** Δt が不揃いだと、等速運動なのに加速度が出るという致命的な誤りが生じます。
   - `requestVideoFrameCallback` が使えない環境では `currentTime` を細かく進める方式にフォールバックし、その旨を画面に警告表示。
3. コマ送り UI（前後ボタン、スライダ）で任意のコマを表示。
4. **画面をタップすると、そのコマの座標が記録される**（手動打点）。打った点は円で表示、番号を振る。
5. 打点済みのコマ一覧と、まだ打っていないコマが分かる表示。
6. 打点のやり直し（1点消去、全消去）。
7. **トリム（解析範囲の指定）**。タイムライン上の2つのつまみ（イン点・アウト点）で、解析に使う区間を切り出す。

### トリムは追跡・背景推定より前に置くこと（処理順が重要）

全体の処理順は次の通りです。

```
動画読み込み → トリム → 追跡・背景推定 → コマ選択 → ストロボ生成
```

**トリムを後回しにすると壊れます。** 背景の中央値推定に無関係な区間が混ざり、コマ間隔の不揃い判定も狂うからです。

生徒の動画には必ず余計な前後が付きます。台車なら手で押している区間と壁に当たった後、振り子なら手を離す前、円運動なら回転が安定する前、斜方投射ならバウンドの前後。特に斜方投射は、バウンド前後で加速度が桁違いに大きくなりスケールが破壊されるため、**一つの放物線だけを切り出せることが必須**です。

### 重要

手動打点は「自動追跡が失敗したときの保険」ではなく、**このアプリの基礎機能**です。シールを貼れない対象、色で追えない対象（回るコマ、落ちる紙、ブランコ、水滴）は自動追跡が通りません。手動打点があれば、それらすべてが測定対象になります。10点なら30秒で打てます。

### 動作確認

適当な動画を読み込み、10コマに打点し、`state.frames` に座標と実タイムスタンプが正しく入っていることをコンソールで確認できること。**コマ間隔が均一でない動画で、t の差が実際に不揃いになることを確認してください。**

## フェーズ2：自動追跡と診断

### やること

1. **色による追跡**。運動する物体に蛍光色の丸シール（中心に黒点）を貼って撮影する前提。
   - RGB ではなく HSV に変換し、色相と彩度で閾値処理する。明るさの変化に強くするため。
   - 既定は蛍光ピンク。色はユーザーが画面上のシールをタップして「この色を追う」と指定できるようにする（タップ位置周辺の平均色相を取得）。
   - 閾値を超えた画素の塊（ブロブ）の重心を座標とする。
   - 複数のブロブが見つかった場合は、**前のコマの座標に最も近いもの**を選ぶ。

2. **固定マーカーによるカメラぶれ補正**（重要）
   - 運動する物体と同じシールを、机や壁など**動かない場所にもう1枚**貼って撮影してもらう。
   - このマーカーの座標を全コマで追跡し、**その変位を運動物体の座標から差し引く**。
   - これだけで、三脚のずれ・手ぶれ・電子式手ぶれ補正（EIS）の影響がまとめて補正できます。EIS は機種によって切れないので、この対策が現実解です。
   - 固定マーカーが無い動画でも動くこと（補正なしで続行し、その旨を表示）。

3. **診断メッセージ**（これが無いと教室で使えません）

   解析前に自動チェックし、問題があれば赤字で具体的に表示：

   | 検出条件 | 表示するメッセージ |
   |---|---|
   | 固定マーカーが N px 以上動いた | カメラが動いています。三脚を固定して撮り直してください |
   | 追跡できないコマがある | ◯コマ目で見失いました。照明を明るくするか、シールの色を指定し直してください |
   | ブロブが著しく細長い（楕円率が閾値超え） | ブレています。スローモーション（120fps以上）で撮り直してください |
   | コマ間隔の不揃いが閾値超え | 撮影モードを変えてください。コマ間隔が一定になっていません |
   | ブロブが見つからない | シールが写っていません。色を指定し直すか、手動で点を打ってください |
   | 全画面の 90% 以上が背景と異なると判定された | 明るさが変化しています。AE をロックして撮り直してください |

   **「解析できませんでした」だけで終わらせないこと。** 生徒は必ず失敗した動画を持ってきます。何が悪いかを言えるかどうかで、教室で使える道具かどうかが決まります。

4. 追跡に失敗したコマは、フェーズ1の手動打点で埋められること。自動と手動が混在して構いません。

## フェーズ3：コマ選択とストロボ画像生成

### 二段構えの処理（メモリ対策として必須）

- **第一パス**（フェーズ1〜2で完了済み）：全コマを走査して**座標と時刻だけ**を保存。画像は保存しない。1000コマでも数十KB。
- **第二パス**（ここ）：生徒がコマ間隔を決めた後、**選ばれた10コマ前後にだけ**シークして画像を合成する。

この分離により、間隔スライダを動かしても即座にプレビュー（点の並びだけ）が返ります。画像合成は「これでいく」と確定してから実行。

### コマ選択 UI

**自由なコマ選択にしないこと。等間隔を強制します。**

Δt が不揃いになった瞬間に速度も加速度もすべて破綻します。UI は次の3つのスライダのみ：

- 開始コマ
- 間隔（何コマおきか）
- 個数（何点使うか）

間隔を動かすと、**加速度ベクトルの矢印群がリアルタイムでプレビュー更新される**ようにしてください。加速度は二階差分なので、間隔が狭いとジッタで矢印が暴れ、広いと曲率のバイアスが乗ります。プレビューがあれば、教師が授業前に「この素材はこの間隔」と決められます。

目安として「コマ間の変位がジッタの10倍以上」を推奨値として自動提案する。

### ストロボ画像の生成方式

**既定：中央値背景 + 全画面差分。これ一本で組んでください。**

「不変の背景の上に、動いたものだけが重なっていく」という方式です。**何が動いているかを事前に指定する必要はありません。**「動いた」という事実だけで拾えます。座標を必要としないので、追跡できない対象（落ちる紙、跳ねる縄跳び、回るコマ、水滴）でもストロボ画像が作れます。

座標が取れているときだけ物体周辺に限定する、というハイブリッドにはしないでください。実装が二系統に分かれ、診断メッセージも倍になります。そして限定は精度問題を隠すだけで解決しません（カーテンが揺れている動画は、追跡も背景推定も両方おかしい）。直すのは撮影条件の側です。

処理は次の通り。

1. トリム後の区間から、**等間隔に20〜30コマ**を抜き出す。連続コマは使わないこと——動きの遅い区間が続くと、そこで物体が背景に混ざります。
2. 画素ごとに**中央値**を取って背景画像を作る。**平均ではなく中央値**（平均だと物体が薄く残ります）。
3. 各コマについて背景との差を計算し、閾値を超えた画素だけを背景の上に描く。
4. 差分は RGB の単純差ではなく、**輝度差と色差を分けて見る**。影は輝度だけ変わって色相が変わらないので、分けると影を落としやすくなります。
5. 得られたマスクに軽いモルフォロジー処理（収縮 → 膨張）をかけ、ノイズの点々を消す。

処理コストは中央値の計算に集中しますが、720p で30コマなら数秒です。第一パスの座標走査と一緒に済ませられます。

**閾値は自動決定し、かつスライダを1本出す**

差分値のヒストグラムは、背景（差ゼロ付近の巨大な山）と物体（小さな裾）に分かれるので、大津の判別分析法で初期値を自動決定できます。

そのうえで、結果を見ながら動かせるスライダを**必ず**出してください。「物体が欠ける ←→ ゴミが写る」の1軸なので、生徒にも意味が分かります。**自動値だけで済ませないこと。教室の照明条件は予測できません。**

**退避先：マーカー切り抜き貼り付け**

背景が動く、露出が変わる、影が消せない——背景差分がどうしても破綻する動画は必ず出ます。そのとき、座標さえあれば確実に動く手段として残してください。座標周辺の半径 R の円だけを背景フレームの上に貼る方式で、閾値も背景推定も不要なので絶対に破綻しません。

「うまくいかない生徒に何と言うか」の答えを一つ持っておく、という位置づけです。既定にはしないこと。

**オプション：比較明合成（lighten）**

`globalCompositeOperation = 'lighten'` で重ねるだけ。暗幕の前で明るい物体、という条件が作れるなら一番きれいになります。条件を作るのが面倒なので、余裕があるときの上位互換として残す。既定にはしないこと。

**共通の注意**

同じ場所を通過する運動（振り子、円運動）では、後のコマが前のコマを覆い隠します。**古いコマを半透明にする**、または輪郭を残す処理を用意してください。

### 番号を必ず振る

各点の脇に 0, 1, 2, … と小さく表示。**振り子のように往復する運動では、点の並びを見ただけでは時間順が分かりません。** 順序が分からなければ速度ベクトルの向きが決められない。番号は消せないようにしてください。

### PNG 書き出し

生成したストロボ画像を PNG で保存できるようにしてください。生徒がレポートや課題研究に貼れます。

## フェーズ4：作図（このアプリの本体）

ストロボ画像の上に、生徒が指で矢印を描きます。**ステップは順序制約付きで、前のステップを終えるまで次に進めません。**

**作図は最初から最後までストロボ画像の上で完結します。別枠には出しません。**③④は隣り合う速度ベクトルの組ごとに繰り返すループで、組を送りながら Δv を軌道上に1本ずつ積み上げていきます。別枠（ホドグラフ）は発展として最後に置きます。

### ① 基準点と位置ベクトル

- 生徒が画面上の任意の点をタップして基準点を決める。
- 基準点から各コマの黒点へ矢印を引く。
- **全コマ分描かせないこと。** N=10 なら10本になり、集中力を使い切ります。最初の3〜4本だけ手描きで、残りは「残りを自動で描く」ボタン。

### ② 速度ベクトル

- 隣り合う位置ベクトルの**先端同士を結ぶ**矢印を描く。
- これが速度ベクトル（正確には平均の速度）。

### ③④は実寸で描く（倍率を掛けない）

**速度ベクトルにも Δv にも倍率を掛けないでください。**②で描いたものをそのまま使う。そうすると、

- v₍k₊₁₎ の先端は **ちょうど次の黒点 r₍k₊₂₎** に乗る
- 前送りした v₍k₎ の先端は **r₍k₎ を r₍k₊₁₎ について折り返した点**

となり、両端が画面上で確かめられる目印になります。倍率を掛けると両方が何もない空中に浮き、合っているかどうかを確かめる手がかりが消えます。

**倍率は、掛けると必ずはみ出します。** 長さの上限だけで頭打ちを決めると、矢印が**どこから生えるか**を見ていないので、斜方投射のように軌道が画面の端に近い素材では突き抜けます（実際に踏んだ）。実寸なら矢印は軌道から1ステップぶんしか外へ出ないので、はみ出しようがありません。

**ただし1ステップぶんは外へ出るので、③④のあいだだけ表示範囲を広げてください。** 軌道にぴったり合わせたクロップのままだと、折り返し点が画面から消えます。折り返し点と持ち上げの弧を含む範囲を計算して広げ、⑤で元に戻す。

代償は Δv が短くなることですが、**それは素材の問題としてそのまま出るほうが正しい**です。Δv が短いということは向きの不確かさが大きいということなので、矢印を伸ばして誤魔化すのではなく、③のヒントで「この間隔では Δv の向きの不確かさが ±◯° あります」と伝えてコマ間隔を広げさせてください。作図の精度は④のハンドルと拡大鏡で稼ぎます。

**⑤も既定は実寸にしてください。**自動で拡大しないこと。拡大が要るときのために倍率のスライダーを1本置き、**⑤⑥と発展のホドグラフで同じ値を使います。**別々の倍率にすると、⑤と別枠を行き来したときに同じ Δv が数倍違う大きさに見えて、対応づけそのものが壊れます（発展の中身は「同じ Δv が2つの表現のどこにいるかを対応づけること」なので、致命的です）。ホドグラフ側は速度ごと同じ倍率で拡大するので、三角形は相似のまま保たれます。倍率は画面に明示すること。

### ③ 速度ベクトルの始点を揃える（組ごとに繰り返す）

隣り合う2本 v₍k₎ と v₍k₊₁₎ の始点を、**ストロボ画像の上で**揃えます。別枠には出しません。

- v₍k₎ は r₍k₎ → r₍k₊₁₎ に、v₍k₊₁₎ は r₍k₊₁₎ → r₍k₊₂₎ に描かれている。つまり **v₍k₊₁₎ の始点はすでに r₍k₊₁₎ にあります**。
- したがって**動かすのは v₍k₎ だけ**。r₍k₎ から r₍k₊₁₎ へ、1本だけ前送りにスライドさせる。v₍k₊₁₎ は動かさない。**2本とも動かす実装にしないでください。**1本だけが動くことで「隣の速度ベクトルを、こっちへ持ってきて比べる」という意図が読めます。
- **必ずアニメーションさせてください（重要）。** 「同じ矢印をこっちへ持ってきた」という動きが、ベクトルは平行移動しても同じもの、という自由ベクトルの概念そのものを見せます。パッと切り替わると、生徒には別物が現れたようにしか見えません。**これは発展のホドグラフに入るときも同じです**（後述）。

- **運搬は「滑らせる」のではなく「持ち上げて運ぶ」。** 軌道と垂直に弧を描いて浮かせ、着地点でぴたりと線の上に降ろしてください。浮かせる量は、浮かせる向きに見えている範囲の6%程度。**線の上を滑らせると、一次元運動では動きが追えません。**速度ベクトルが全部おなじ直線に乗るので、同じ線の上を矢印が動いても「どれが、どこから、どこまで」が読めない（自由落下の実測で判明）。浮かせれば軌跡が追えます。ずらしてはいけないのは④で先端どうしを結ぶ瞬間であって、運んでいる途中は演出の領分です。**着地時のずれはゼロにすること。**

- **運んでいるコピーは、もとの速度ベクトルと色を変えてください。** 淡くするだけでは引きの映像で溶けます。加えて、**もとの場所の v₍k₎ は実体として濃いまま残す**こと。出発点と運搬中のコピーが同時に見えていないと、どこからどこへ動いたのかが読めません。2本には名札（v₍k₎ / v₍k₊₁₎）を付け、どれがどの矢印かを色だけに頼らせないこと。
- **注目中の組以外は、すべて減光してください。** 他の位置ベクトル・速度ベクトルは薄いグレーに落とし、r₍k₊₁₎ に丸ハイライトと「k → k+1」のラベルを出す。画面上の濃い矢印は常に2本だけ。**これが逐次方式の生命線です。**画面が混むと、別枠方式で起きていた「今どの点の作業なのか分からない」がそのまま戻ってきます。一次元運動では他の速度ベクトルも同じ直線上に並ぶので、減光は二次元より強めに効かせること。

ラベルは「集める」ではなく「**始点を揃える**」にしてください。操作と一致します。

### ④ Δv を描いて、軌道上に置く（組ごとに繰り返す）

**入力はハンドル方式にしてください（スマホで決定的）。**

③が終わった時点で、v₍k₎ の先端に**長さゼロの矢印とハンドル（つまむ輪）**を置きます。生徒はその輪を動かして先端を決め、「決定」を押して確定する。一発のドラッグで確定させないこと。

- **Δv の始点は生徒が選ぶものではありません。** 必ず v₍k₎ の先端に置かれる。そこを指で正確に押さえさせるのは思考ではないので、アプリが引き受けてよい部分です。一方、**もう一方の先端がどこかを見つけること**が④で観察したい思考なので、そこは手つかずで残します。磁石を掛けない方針は変わりません。
- **初期の矢印は長さゼロにすること。** 何らかの向きを持たせると答えを示唆します。とくに v₍k₊₁₎ の向きを初期値にしてはいけません——「加速度は速度の向き」という典型的な誤概念を、アプリのほうから示唆することになります。
- **決定するまで何度でも動かし直せること。** スマホでは指が先端を隠すので、拡大鏡を見ながら追い込む余地が要ります。一発勝負だと拡大鏡が役に立ちません。
- **掴む判定は単純に。** キャンバスのどこを触っても先端が動く、でよい。「ハンドルの近くを押したときだけ掴む」にすると、指の太さで誤爆します。
- ドラッグ中は仮の矢印を別に出さず、**ハンドルそのものを動かす**。離す前に決まる形が見えているほうが調整しやすい。
- **④は正誤を判定しません。** 差し戻すのは「まだ一度もハンドルに触れていない」ときだけで、長さでは判定しない。生徒がハンドルを始点に戻して「Δv = 0」と答えたなら、それはその生徒の答えです。正しいかどうかは⑥が言う。磁石を掛けないのと同じ理由で、ここで先回りして正解の方向へ誘導しないこと。
- そのぶん**⑥でゼロの回答を必ず拾ってください。** 「ゼロとしましたが、実際にはゼロではありませんでした」「ゼロで合っています（ゼロベクトルもベクトルです）」のように、無評価で素通りさせない。

確定した Δv が（加速度の向きを示す）。
- 描けたら、Δv を**共通始点 r₍k₊₁₎ へ平行移動**します。作図した直後の Δv の始点は v₍k₎ の先端なので、この置き直しが1回だけ必要です。移動先は目の前の共通始点なので、三角形の一辺を頂点へ持ち帰るだけの自明な動きになります。ここも 0.3秒程度のアニメーション。
- 置いたら v₍k₎ と v₍k₊₁₎ をフェードアウトし、**Δv だけを r₍k₊₁₎ に残す**。
- **k を1つ進めて③に戻る。** 「3 / 9 組」のようなカウンタを常時表示すること。

つまり1組あたり、短い移動が2回です。

```
1. v₍k₎ が r₍k₎ → r₍k₊₁₎ へスライド（v₍k₊₁₎ は動かない）
2. 生徒が2本の先端を結んで Δv を作図
3. Δv が r₍k₊₁₎ へスライド、v₍k₎ と v₍k₊₁₎ はフェードアウト
4. k を1つ進める
```

**アニメーションの速さは切り替えられるようにしてください。** 既定はゆっくり（揃える0.8秒、置き直し0.55秒）。加えて、**Δv が着地したあと次の組へ移るまでに 0.3 秒の間を置くこと。**この間が無いと「動いた→もう次」になって速すぎると感じます（実機で指摘されました）。慣れた人向けに「アニメを速く」のトグルを置き、`localStorage` に覚えさせる。授業で繰り返し使うので、毎回チェックし直させないこと。

**手描きは最初の1〜2組だけです。** 残りは「残りを自動で」ボタンで、同じアニメーションを高速で流します。生徒が自分でやった操作がそのまま速回しで続く、という連続性が大事なので、**自動分だけ演出を変えないでください**（一括でパッと表示する、アニメーションを省く、等）。

### ⑤ Δv だけを残す

全ての組が終わったら、位置ベクトル・速度ベクトル・補助線をすべて消し、**軌道上の Δv だけ**を残します。**ここがこの教材の到達点です。**

- 円運動 → すべての矢印が中心を向き、放射状に並ぶ
- 斜方投射 → 全コマで真下を向き、長さが同じ
- 単振り子 → 端で接線方向を向く
- バネ振動 → 常に釣り合いの位置を向き、離れるほど長い

③④は一組ずつしか見えないので、**全体の傾向が見えるのはここが最初です。** 逐次方式が失う一望性を回収するステップなので、絶対に省略しないでください。これが無ければ、④までの丁寧な作図が回収されません。

**ただし、速度ベクトルを消しっぱなしにしないこと。** ⑤に入った時点の既定は「Δv だけ」でよいのですが、レイヤーの切り替え（①位置／②速度／Δv／予測）は⑤でも出したままにして、速度を戻せるようにしてください。Δv だけを見て向きの傾向をつかんだあと、速度と並べて「速度がゼロでも Δv は残る」を確かめる、という往復が要ります。

### 一次元運動での表示ルール（③④⑤共通）

台車・自由落下・バネの単振動では、v₍k₎ と v₍k₊₁₎ が**同じ直線上に乗ります**。二次元と手順は完全に同じですが、表示だけ3点の手当てが要ります。

**1. 2本が重なる。** ③で始点を揃えると、2本は同一直線上で入れ子になります（等加速度なら短い v₍k₎ の中に長い v₍k₊₁₎ が重なり、**はみ出した先の部分がそのまま Δv**）。1本に見えないよう、**v₍k₎ は輪郭だけの太い矢印、v₍k₊₁₎ は塗りの細い矢印**のように下敷き／上乗せで描き分けてください。

**平行にずらして逃げないこと。** 始点を縦にずらすと Δv が斜めになり、作図として嘘になります。一次元で「速度が伸びた分が Δv」という読み方が成立するのは、2本が同じ直線上にあるからです。別枠の階段モードがこのずらしをやっていましたが、あれは表示上の仕掛けで、本筋には持ち込みません。

**2. 等速では作図が縮退する。** 2本が完全に重なり、先端も一致するので、Δv の長さがゼロになります。**エラーにしないでください。**ハンドル方式なら、先端をその場でタップして決定すればそのまま Δv = 0 の回答になるので、特別扱いは要りません。ゼロベクトルもベクトルである、というのはここでしか教えられません。

「2本が重なっています」と案内を出す判定には、**点の間隔を基準にしてください**（Δv の中央値が点間隔の3%未満、など）。画面の拡大率にもクロップにも左右されず、「2つの先端のあいだに指で動かせる隙間があるか」という事実をそのまま測れます。

**ジッタの見積もりで判定してはいけません。**ジッタは間隔1コマの二階差分から作られていますが、等加速度運動ではその二階差分こそが信号なので、自由落下・斜面の台車・円運動まで「重なっている」と誤判定します（2回踏みました）。

**3. ⑤で Δv が軌道の上に乗る。** 二次元なら Δv は軌道の外へ出ますが、一次元では黒点の列と同じ直線に並び、読めません。**⑤の一覧に限り、Δv の列を軌道と垂直に平行移動して並べてください。**ずらす向きは階段モードと同じ判定（主に縦の運動なら右、主に横の運動なら下）が使えます。⑤は比較のための表示であって作図ではないので、ここでのずらしは嘘になりません。③④ではずらさない、という切り分けを守ること。

### ⑥ 答え合わせ

- 自動算出した矢印を**重ねて表示**する。別画面にしないこと。ズレて見えること自体が議論の材料になります。
- **加速度は定量計算しないでください。** 自動算出した速度ベクトルの先端同士を結んだもの、として求めます。生徒の作図と正解が同じ作図操作で得られるので、比較が対等になります。数値で出すと、単位もスケールも違うものを並べることになり、ズレの原因が作図なのか計算なのか分からなくなります。
- 判定は**向き中心**に。許容角度（±15°程度）を設け、「向きは合っています」「向きが◯◯度ずれています」と返す。
- **重ねる場所は軌道上です。** ⑤で残した生徒の Δv の上に、自動算出の Δv を同じ始点 r₍k₊₁₎ から重ねる。別枠で比較しないこと。
- **⑥に進めるのは、⑤に到達した後だけ**にしてください。先に見られると生徒は必ず先に見ます。到達した後は何度でも重ねられてよい。

### 時刻の半コマずれ（実装上の注意）

②で先端同士を結んだ矢印は、r₀ と r₁ の**中間時刻**の速度を表します。そして④の Δv は、その中間時刻同士のさらに中間、つまり**元のコマの位置**に対応します。

```
位置    r₀      r₁      r₂      r₃      r₄
速度       v₀.₅    v₁.₅    v₂.₅    v₃.₅
加速度         a₁      a₂      a₃
```

つまり v₀.₅ と v₁.₅ から作った Δv が属するのは、r₀ ではなく **r₁** です。逐次方式では、この r₁ がそのまま③で始点を揃える場所であり、④で Δv を置く場所になります。揃える先と置く先が同じ点になるのは偶然ではなく、Δv が r₁ に属するからです。

一般化すると、v₍k₎ と v₍k₊₁₎ から作った Δv は **r₍k₊₁₎** に属します。この対応を間違えると、矢印が1コマぶんずれた位置に描かれます。**コード内でインデックスの対応を明示的にコメントすること。**

なお円運動については、Δv = (r₍k₊₂₎ − r₍k₊₁₎) − (r₍k₊₁₎ − r₍k₎) = r₍k₊₂₎ − 2r₍k₊₁₎ + r₍k₎ が、等角間隔なら r₍k₊₁₎ から中心へ**厳密に**向きます（中心を原点、r₍k₊₁₎ を (R, 0)、角間隔 θ とすると 2R(cos θ − 1, 0)）。近似ではないので、ズレが見えたら撮影面の傾きか追跡誤差を疑ってください。

### 発展：ホドグラフ（別枠）

**ここは初学者の本筋ではありません。⑤まで到達した生徒に、追加で提示するものとして実装してください。**

速度ベクトルの始点を1つの原点に集めた図が、**ホドグラフ（速度図）**です。先端が描く軌跡が運動の性格を表します。加速度とは「ホドグラフ上を先端が動く速さ」であり、位置の軌跡に対する速度とまったく同じ関係にあります。ここまで見せられれば、微分の階層構造が二段で通ります。

**なぜ本筋から外すか。** 軌道上の点と、別枠の第k本目とを対応づけながら Δv の向きを考えると、対応づけのコストでワーキングメモリが埋まり、肝心の思考にリソースが回りません。とくに**円運動では、軌道も円、ホドグラフも円**になります。この同型性は物理として最も美しい部分ですが、初学者にとっては「2つの円のどちらを見ているのか分からない」という最悪の混同源です。それが美しさとして見えるのは、③〜⑤で「Δv は中心を向く」が腑に落ちた後だけです。

**提示の仕方。** ⑤で軌道上に並んだ Δv と、別枠のホドグラフを**行き来させてください。**同じ Δv が2つの表現のどこにいるのかを対応づけることが、この発展の中身です。片道で見せて終わりにしないこと。

**別枠へ入るときの「集まる」アニメーションを省かないでください。** 軌道の上の速度ベクトルが共通の原点へ1秒かけて滑って集まり、そのあとホドグラフの表示になる、という順序です。③で軌道の上でやった「始点を揃える」を、今度は全部まとめてやるのがホドグラフなので、**この動きが無いと別枠は「どこから来たのか分からない抽象図」に戻ります。**①②と③④が同じ操作だという構造の繰り返しが、ここでもう一段効く場所です。

**現象によってホドグラフの形が違うため、別枠の見せ方を統一できません。** 加速度が一定なら全部集めると効きますが、加速度が回転する運動では一組ずつ見ないと読めず、一次元運動では線分に退化して読めなくなります。

以下の3モードを実装し、プリセットで既定を指定してください。生徒が切り替えることもできるようにする。

**全集合モード** — 速度ベクトルを全部まとめて原点に集める。Δv がすべて同じ向き・同じ長さになる運動でのみ有効。10本の矢印がぴたりと重なること自体が結論になる。

**ペア送りモード** — v₍n₎ と v₍n₊₁₎ の**2本だけ**を表示し、スライダで組を送る。送るたびに先端の位置が薄い点として残り、最後にホドグラフの形が浮かび上がる。等速円運動なら、一組ずつ「Δv が中心を向く」を確認しながら、気づけば速度の先端が円を描いている。加速度が向きを変える運動ではこれが既定。

**階段モード** — 一次元運動用。始点を原点に集めると全部が同一直線上に重なって読めないため、始点を縦に少しずつずらして階段状に並べる。先端を結んだ線が Δv を示す。等速なら段差ゼロ（先端が垂直に揃う）、等加速度なら段差が一定。バネの単振動は横軸を時間に取る（ホドグラフが退化する以上、時間軸を足して次元を回復するしかない）。

**現象ごとの既定と勘所**

| 現象 | ホドグラフの形 | 勘所 | 発展での既定 |
|---|---|---|---|
| 直線運動・水平（等速） | 一点 | Δv がゼロでもベクトル | 階段 |
| 直線運動・水平（等加速度） | 直線上に等間隔 | Δv が一定。進行方向を向く | 階段 |
| 直線運動・斜面 | 直線上に等間隔 | Δv が斜面に平行。真下ではない | 階段 |
| 直線運動・鉛直（自由落下） | 鉛直線上に等間隔 | Δv が真下・一定。斜方投射と同じ | 階段 |
| 斜方投射 | 鉛直線上に等間隔 | 全部が真下・同じ長さ | 全集合 |
| 等速円運動 | 円 | 常に中心向き。速度もまた円運動している | ペア送り →（追加で）全集合 |
| 単振り子 | 原点を通る弧 | 端で v=0 でも Δv は残る | ペア送り |
| バネ振動 | 線分を往復 | 常に釣り合い位置向き、変位に比例 | 階段（時間軸に展開） |

**斜面の台車と斜方投射は対比させる価値があります。** どちらも加速度一定ですが、Δv の向きが鉛直下向きか斜面平行かで異なる。「重力は下向きなのに加速度は斜面方向」という分力の話に、ホドグラフから入れます。

**本筋の出口は⑤です。** 別枠の見え方が現象ごとにバラバラでも、本筋は軌道上に並んだ Δv に着地しているので、勘所はその時点で既に伝わっています。単振動の別枠がどれだけ読みにくくても、⑤で釣り合いの位置を向く矢印が並んでいれば損はありません。**発展が読めないことを理由に、本筋まで疑わせない設計にしてください。**

**授業で扱う順序**（プリセットのタイル配置もこれに合わせる）：台車（水平・斜面）→ 自由落下 → 斜方投射 → 円運動 → 振り子・バネ。**自由落下は斜方投射の直前に置いてください。**どちらも Δv が真下・一定で、まったく同じ図になります。第1弾の落下比較アプリが定性的に見せたことを、ここで作図として回収するのがこの並びの狙いです。**本筋の①〜⑤はどの運動でも同じ操作なので、この順序で手順を覚え直す必要はありません。**発展のホドグラフを併せて見せるなら、加速度一定の斜方投射（全集合が効く）で形を覚え、円運動（ペア送り）で回転を見て、最後に退化する一次元運動（階段）を扱うのが読みやすい順です。

### 矢印の引き方とスナップ（作図ステップ共通）

**基本はドラッグです。** 始点から終点まで指を滑らせて矢印を引く。ただしタップ式（始点をタップ→終点をタップ）を別モードとして分けないでください。**タッチ開始と終了の距離が閾値以下ならタップ、それ以上ならドラッグ**と自動判定し、どちらの操作でも同じ結果になるようにする。生徒に操作方式を選ばせないこと。指先で終点が隠れる問題は、共通仕様のルーペで対処します。

**磁石（スナップ）はステップごとに切り替えます。** 座標はアプリが既に持っているので、距離判定だけで実装できます。

| ステップ | スナップ | 吸着先 |
|---|---|---|
| 基準点の指定 | あり | 最寄りの黒点 |
| ① 位置ベクトル | あり | 黒点の中心 |
| ② 速度ベクトル | あり | 黒点の中心 |
| ③ 始点を揃える | ― | 自動処理 |
| ④ Δv | **なし** | ― |

**④にスナップをかけないでください。** 吸着先は「速度ベクトルの先端」になりますが、自動で合わせてしまうと、生徒は先端を結ぶという操作の意味を考えずに済んでしまいます。ここが本教材で観察したい思考の場所です。①②は磁石が精度を保証して生徒が向きと構造に集中できるようにし、その代わり④は自力で合わせさせる、という切り分けです。

### 構造の可視化（あると効果が大きい）

**①②と③④はまったく同じ操作です。**

- ①：始点が基準点に揃った矢印群 → ②：先端同士を結ぶ
- ③：始点を揃え直す → ④：先端同士を結ぶ

④の画面の隅に①②のミニ図を並べて表示してください。「位置→速度」でやったことをそのまま一段上げると「速度→加速度」になる、と生徒が自分で気づけば、微分の階層構造が一発で入ります。

逐次方式では、この対応がさらに見やすくなります。③④で扱っている組は常に r₍k₎ r₍k₊₁₎ r₍k₊₂₎ の3点なので、**ミニ図にはその3点ぶんの①②だけを描いてください**（全コマ分ではなく）。上の段と下の段で、同じ3点について同じ操作をしていることが一目で分かります。

## フェーズ5：自動モードと予測ステップ

### 自動モード

①〜⑥を自動で表示するモード。授業での提示用、教師の下見用。③④の組送りも、手書きモードとまったく同じアニメーションを自動で流すこと。

**内部的には手書きモードと同じパイプラインに、作図ステップをスキップするフラグを一つ立てるだけ**で実装してください。コードを二系統に分けないこと。

ただし、**手書きを毎回やらせる必要はありません**。①〜⑤のフル手順が要るのは概念を立ち上げる最初の一回だけです。三学期の円運動で毎回同じ作図をさせたら生徒は飽きます。二回目以降は自動で出して議論に時間を使う、という運用を想定してください。

### 予測ステップ（教師が ON/OFF できるフラグ）

解析の**前**に、「加速度はどっちを向くと思う？」を問う画面を挟みます。

**予測 → 検証で驚きが生まれるのは、生徒が間違った予測に賭けた後だけです。** 何となく選んで結果を見た場合、人は「そう思ってた」と記憶を書き換えます。そのための設計：

1. 運動ごとの四択を出す（プリセットに含める）。
   - 直線運動：水平・斜面・鉛直で別の四択（フェーズ6参照）。**水平は等速でも等加速度でも同じ四択を使う**。答えが運動によって変わることで、知識での正解を封じる
   - 円運動：中心向き／接線方向／進行方向／外向き
   - 斜方投射：**上昇中・頂点・下降中を別々に3回聞く**（単に「加速度の向きは？」と1回聞くと「重力だから下」と知識で正解されてしまい、理解が確認できません。誤答が集中するのは頂点です）
   - **選択肢には A/B/C/D の記号を振る。文言と並び順は、後述する集計アプリ側の選択肢と完全に一致させること。**
2. 選択後、「**あなたの予測：B（接線方向）**」と画面に大きく残す。
   - **生徒はこの画面を見て、別の集計アプリに自分の選択を転記します。** 転記のたびにこの画面へ戻る往復が起きないよう、記号を大きく、消えない位置に表示すること。
   - 斜方投射のように複数問ある場合は、「A / D / D」のように**3つまとめて一覧表示**し、一度の転記で済むようにする。
3. **選んだ予測を保持する。** ⑥の答え合わせで、自分の予測矢印を薄い灰色で重ねて表示する。逃げ場を無くすこと。軌道上の Δv に重ねるので、予測も軌道上の同じ点を始点にして描く。

実装としては「もう一本、生徒の矢印を保持する」だけなので、既存の手書きベクトルの仕組みがそのまま使えます。

**このアプリでは分布の集計・共有は行いません**（別の集計アプリを使用）。予測の集計機能、サーバー送信、回答の保存・共有機能は実装しないでください。アプリの役割は「選ばせる・記号を見せる・⑥で重ねる」の3つだけです。

### トップページ

入口は「手書き／自動」の選択ではなく、**運動の種類のタイル**にしてください。

| タイル | 内容 |
|---|---|
| 直線運動（台車・自由落下） | 一次元。最初の単元向け。次画面で 水平／斜面／鉛直 を選ぶ |
| スーパーボールの斜方投射 | 二次元。最大の見せ場 |
| 単振り子 | 二次元。発想の原点だが最難 |
| バネの単振動 | 一次元。縦向き |
| ターンテーブルの円運動 | 二次元。概念テストとして完成度が高い |
| その他の運動（自由測定） | プリセットなし。入口は分けず、6つ目のタイルとして並べる |
| ストロボ画像をつくる | ベクトル作図なし。動画からストロボ画像を作るだけ |

**「ストロボ画像をつくる」タイルについて**

追跡も座標も不要な独立機能です。処理は「動画読み込み → トリム → 背景差分 → コマ選択 → 生成 → PNG 書き出し」だけ。

シールを貼れない対象がすべて使えるので、**アプリの中で最も使用回数が多い機能になる可能性があります**。落下する紙、衝突する球、波の伝わり、回転するコマ、跳ねる縄跳び。物理以外でも体育の動作分析や生物の運動に使えます。

生成後に「このままベクトルも描いてみますか？」という導線を置き、座標さえ取れれば①〜⑥に進めるようにしてください。ストロボ画像を作りに来た生徒が、ベクトル作図に入る入口になります。

手書き／自動は次の画面の小さなトグル。

### プリセットが持つ値

タイルを選んだ時点で流し込む：既定のコマ間隔、追跡する色、切り抜き半径、画面の縦横、一次元/二次元の別、予測の四択、そして「この運動で注目してほしいこと」の一文。

**プリセットの正体は初期値です。** 自由測定モードは、これを既定値スタートにして生徒が全部動かせるようにするだけ。新規実装ではなく、プリセット選択のスキップとして作ってください。

### 運動ごとの実装上の注意

**直線運動（台車・自由落下）**：タイルは1枚のままにし、**次画面で「水平／斜面／鉛直（自由落下）」を選ばせてください。**手書き／自動のトグルと同じ画面です。独立タイルを3枚立てると入口が重くなり、しかも並びの先頭に一次元が3枚続きます。

**等速か等加速度かで分けないでください。** それは生徒が Δv を見て判定する結論であって、入口で名乗らせると予測が予測でなくなります。実際、プリセットが持つ値（画面の向き、クロップの縦横比、コマ間隔、段の向き、⑤で Δv 列をずらす向き、予測の四択）は、等速か等加速度かでは1つも変わらず、**軌道が水平か斜めか鉛直かだけで決まります。**

| 次画面の選択 | 画面 | 軌道 | 予測の四択 |
|---|---|---|---|
| 水平（台車） | 横 | 水平 | 進行方向／進行方向と逆向き／真下／加速度はゼロ |
| 斜面（台車） | 横 | 斜め | 斜面に平行／真下／斜面に垂直／加速度はゼロ |
| 鉛直（自由落下） | 縦 | 鉛直 | 真下／進行方向／上向き／加速度はゼロ |

**水平の四択は、等速でも等加速度でもそのまま使えます。** 手で押して手を離した台車なら答えは「ゼロ」、滑車とおもりで引いた台車なら「進行方向」。同じ問いの答えが運動によって変わるので、生徒は知識で当てられず、Δv を見るしかなくなります。**水平＝等速と決めつけた設計にしないこと**（おもりで引く配置は等加速度直線運動の定番実験です）。等速のときの「ゼロベクトルもベクトル」も、この四択の中でしか成立しません。Δv ≒ 0 の扱いはフェーズ4の「一次元運動での表示ルール」2を参照。

**鉛直（自由落下）固有の値**：画面は縦で固定。軌道が縦に細いため、クロップの縦横比に合わせてキャンバス自体も縦長にしないと倍率が上がりません（縦横比を動画に固定したままだと高さが先に詰まります）。左右に余地を残して基準点を軌道の真横に置けるよう、クロップの縦横比には下限を設けること。コマ間隔は水平の台車より小さめ。⑤で Δv 列をずらす向きは右。

**斜面（台車）固有の注意**：四択に「真下」を必ず残してください。**ここが最大の誤答先であり、「重力は下向きなのに加速度は斜面方向」という分力の話への入口です。**

**斜方投射**：バウンド前後は加速度が桁違いに大きくスケールが破壊されます。**解析範囲を一つの放物線に限定する UI（開始・終了コマの指定）が必須**。

**単振り子**：端では動きが遅く、コマ間隔を小さくすると変位が 1mm 程度になりノイズに埋もれます。**まさに見せたい場所が一番測りにくい。** コマ間隔の既定値を大きめ（0.1秒程度）にし、「端のコマがサンプル点に一致する」ように開始コマを微調整できるノブを用意すること。

**円運動**：撮影面が平行でないと軌道が楕円に写り、加速度が中心を向きません。真上から撮るのは難しいので、**円盤を縦に立てて横から撮る**構成を推奨する旨をアプリ内に表示。

円運動にはコマ選択の制約が2つあります。**どちらもプリセットの既定値とバリデーションで担保してください。**

- **コマ間隔を細かくしすぎない。** |Δv| / |v| ≒ θ（θ はコマ間の回転角）なので、間隔を詰めるほど Δv が潰れて向きが読めなくなります。**1ステップ 30° 前後（1周あたり12点程度）を既定**にすること。このとき |Δv| は |v| の約半分で、十分読めます。15° だと約 1/4 で、そろそろ厳しい。
- **1周を超えさせない。** 周回すると同じ位置に別の周の Δv が積み重なり、⑤の放射状の図が濁ります。選択範囲が1周を超えたら警告を出すか、既定で1周以内に収める。

### サンプル動画の同梱

50分の授業で「撮影→追跡→作図→議論」は入りません。各運動につきお手本動画を1本ずつ内蔵し、アップロードせずに試せるようにしてください。撮影が失敗しても授業が止まらない保険になります。

### 自由測定モードの「お題リスト」

空のアップロード画面を出すと、ほとんどの生徒は何も上げません。**20個程度の「測ってみたいことリスト」を並べてください。**

自転車のペダルの一点／エスカレーターの手すり／落ちる紙と丸めた紙／ブランコ／シャボン玉／自販機から落ちる缶／坂を転がるペットボトル（中身入りと空）／回転いす／ヨーヨー／バスケのシュート／扇風機の羽根の先端／砂時計の砂面

「自由にどうぞ」より「これ測れる？」の方が手が動きます。

自由モードでも予測ステップは残せます。固定の四択は作れませんが、「解析する前に、加速度の矢印がどこを向くと思うか一本描いてから進む」という操作を挿してください。自分でお題を選んだ場合、予測が外れる確率はプリセットより高く、ここが自由モードの一番おいしい部分です。

## 撮影ガイド（アプリ内に常時表示する内容）

アップロード画面に以下を表示：

**必ず守ること**
- カメラを固定する（スタンド・三脚）
- 運動が起きる面と、カメラの撮像面を平行にする
- 少し離れてズームで撮る（近くから広角で撮ると遠近で矢印が歪みます）
- **AE/AF をロックする**（iPhone なら長押し）。露出が動くと全画面が差分と判定され、ストロボ画像が破綻します
- **運動面と背景の間に距離を取る**（台車なら机の縁で走らせて背景を壁にする、振り子なら窓際で振る）。影が背景に落ちにくくなり、ストロボ画像がきれいになります

**できれば**
- スローモーション（120fps 以上）で撮る。通常の30fpsだと室内では露光時間が長く、動く物体が尾を引いて中心が定まりません
- 明るい場所で撮る
- ズームは録画前に決め、録画中は触らない
- 動かない場所にも同じシールを1枚貼る（カメラぶれ補正用）

自由測定モードでは、**「カメラを固定して、運動面と平行に撮る」の一点だけ**を常時表示してください。守るべきルールが一つだと分かっていれば、生徒はけっこう守ります。

## 縮尺について

向きの議論だけなら不要です（矢印の向きは画素座標のままで正しく出ます）。定量まで扱う場合は、**運動面と同じ平面に**物差しを置いて一緒に撮り、画面上で2点をタップして実長を入力する UI を用意してください。手前や奥に置くと遠近で誤差が入ります。
