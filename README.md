# 運動ベクトル可視化アプリ

高校物理向け。生徒が撮影した運動の動画から、**速度ベクトルと加速度ベクトルを生徒自身に作図させる**ための教材。
「速度がゼロなら加速度もゼロ」という誤概念を、目で見て崩すことが目的。

**答えを表示するアプリではなく、生徒に作図させるアプリ。** 自動表示を先に出す設計にしないこと。

実装：**フェーズ1〜6すべて**（座標取得／自動追跡／ストロボ画像／作図①〜⑥／自動モードと予測／運動タイルとプリセット）

**作図の本筋は、最初から最後までストロボ画像の上で完結する。別枠には出さない。**
③④は隣り合う速度ベクトルの組ごとに繰り返すループで、組を送りながら Δv を
軌道上に1本ずつ積み上げる。

```
① 位置        基準点から各コマの黒点へ
② 速度        隣り合う位置ベクトルの先端どうしを結ぶ
③ 始点を揃える  v_k だけを r_k → r_{k+1} へ前送り（v_{k+1} は動かさない）  ┐ 組ごとに
④ Δv          先端どうしを結び、それを r_{k+1} へ置く                    ┘ 繰り返す
⑤ Δv だけ     位置・速度を消して軌道上の Δv だけを残す（到達点）
⑥ 答え合わせ   自動算出した Δv を軌道の上に重ねる
発展           ホドグラフ（別枠）。⑤⑥から呼び出す
```

## 使い方（開発）

ビルドは不要。`index.html` をブラウザで開くだけ。

- ローカル確認：ファイルをダブルクリックで開ける（ES Modules を使っていないため `file://` でも動く）
- 公開：このフォルダごと GitHub に置き、GitHub Pages を有効にする
- 1ファイル版が要るとき：`python3 build.py` → `dist/index.html`（オフライン配布用。ふだんは不要）

### 読み込み方式

ES Modules ではなく、名前空間 `HG` に載せる IIFE を `index.html` から順に読む方式。
理由は、`file://` でダブルクリックしても動くこと（ES Modules は CORS で弾かれる）と、
連結するだけで1ファイル版が作れること。

**ファイルを増やしたら `index.html` の `<script>` の並びに追記すること。** 依存の浅いものから順に並べる。

## イベント

モジュールは互いを直接呼ばず、`HG.bus` を通す。

| イベント | 発火するところ | 意味 |
|---|---|---|
| `video:loaded`   | video/loader   | 動画のメタデータが確定した |
| `frames:scanned` | video/scanner  | 全コマの実時刻を取得し終えた |
| `frame:changed`  | video/frames   | 表示コマが変わった（シーク完了後） |
| `points:changed` | core/points    | 打点が増減した |
| `trim:changed`   | ui/controls    | イン点／アウト点が変わった |
| `view:changed`   | video/frames   | 回転・リサイズなど表示条件が変わった |
| `selection:changed` | ui/selection | 使うコマ（開始・間隔・個数）が変わった |

作図中（`HG.draw.active()`）は、自動の加速度プレビューを止める。答えを先に見せないため。

`points:changed` は自動追跡の完了時にも飛ぶ（`video/tracker.js`）。

購読の配線は `js/main.js` に集約してある。

## お手本動画（samples/）

各運動につき1本、アップロードせずに試せる動画を内蔵できる。50分の授業で
「撮影→追跡→作図→議論」は入らないし、撮影が失敗しても授業が止まらない保険になる。

いま入っているのは**合成の動作確認用**（円運動・斜方投射）なので、実写に差し替えてほしい。

```
samples/ に動画を置く（短く小さく。数秒・720p 以下で十分）
python3 tools/make_samples.py          # js/presets/samples.js を作り直す
presets.js の sampleKey をファイル名（拡張子なし）に合わせる
```

**なぜ埋め込むのか。** `file://` で開いたページから `<video src="samples/x.webm">`
を読むと canvas が汚染され、`getImageData` が使えなくなる（追跡もストロボも
できない）。data: URI なら汚染されないので、ダブルクリックで開いても動く。
GitHub Pages 経由なら素のパスでも問題ないので、埋め込みが無い場合は
パスで読み、汚染を検出したらその旨を表示する。

## 変えてはいけない約束

1. **コアデータ構造**（`js/core/state.js`）— フィールドの意味・単位・名前を変えると後続フェーズが壊れる。
2. **座標系**（`js/core/coords.js`）— 内部処理は画面座標（y は下向き）で統一。物理座標へは表示・出力の直前だけで変換する。
3. **座標は元解像度のまま保持する** — 表示用の縮尺（`HG.view.scale`）と解析用の座標を混ぜない。
4. **時刻は実測値** — 公称 fps から計算しない。Δt が不揃いだと等速運動なのに加速度が出る。
5. **`x/y` と `rawX/rawY` を混ぜない** — `rawX/rawY` は画像上の実位置（点を映像に重ねる表示用）。
   `x/y` はカメラぶれ補正を掛けたあとの座標で、下流（作図・ストロボ・書き出し）はこちらを使う。
   補正を使わないときは同じ値になる。補正の掛け直しは `HG.points.applyCorrection()` 一本。
6. **時刻の半コマずれ** — `velocityVectors[k]` は r_k→r_{k+1}（中間時刻 k+0.5 の速度）、
   `deltaVVectors[k]` は位置 **r_{k+1}** の加速度。③で始点を揃える点、④で Δv を
   置く点、⑥で重ねる点は、いずれも r_k ではなく **r_{k+1}**。揃える先と置く先が
   同じ点になるのは偶然ではなく、Δv が r_{k+1} に属するから。
   対応は `HG.drawing.posIndexOfDeltaV()` を必ず通すこと。

```
位置    r₀      r₁      r₂      r₃      r₄
速度       v₀.₅    v₁.₅    v₂.₅    v₃.₅
加速度         a₁      a₂      a₃
```

### ネタバレの扱い

「予測 → 検証」で驚きが生まれるのは、生徒が結果を知らずに賭けたときだけ。
そこで、**結果より先に答えを見せる文と表示を画面から外してある**。

| 隠すもの | どこで見せるか |
|---|---|
| プリセットの note（この運動で何が起きるか） | ⑤以降の「解説」（Δv が出そろってから） |
| 加速度のプレビュー（橙の矢印） | 既定で OFF。教師用チェックボックス |
| 推奨間隔の解釈（「Δv ≒ 0 が結論」など） | 測定の話だけ残し、解釈は解説へ |
| 撮影の注意に混ざった答え | 「加速度の向きが正しく出ません」と言い換え |
| 別枠のモード名・タイルの副題 | 動作の説明に置き換え（別枠自体が発展なので本筋では出ない） |

**新しく文を足すときは、それが解析の前に出るかどうかを必ず確かめること。**
`shootTips` と `sub` は解析前に出る。`note` は解説なので書いてよい。

### 別枠をやめて、軌道の上で組ごとに作る形にした（設計変更）

以前は別枠（ホドグラフ）で速度ベクトルを集約し、そこで作った Δv を最後に
軌道へ描き戻していた。**円運動で「いまどの点の作業なのか」が読めなくなる**のが
きっかけで、本筋を組送りに変えた。

理由は2つ。軌道上の点と別枠の第k本目を対応づけながら Δv の向きを考えると、
対応づけのコストでワーキングメモリが埋まり、肝心の思考にリソースが回らない。
そして**円運動では軌道も円・ホドグラフも円**になるので、初学者には2つの円の
区別がつかない。この同型性が美しさとして見えるのは、③〜⑤で「Δv は中心を向く」が
入った後だけ。別枠は発展に降ろし、⑤の軌道上の Δv と行き来させる形にした。

なお、この形自体は旧版の「1点ずつ見る」として既に実装されていたものを、
本筋へ昇格させたもの。前送りの向き（r_k にあった速度を r_{k+1} へ）も同じ。

**動かすのは v_k だけ。** v_{k+1} の始点はもともと r_{k+1} にあるので、
2本とも動かす必要はない。1本だけが動くことで「隣の速度ベクトルを、こっちへ
持ってきて比べる」という意図が読める。前送りではなく v_{k+1} を r_k へ
後送りすると、共通始点が r_k になり、あとで Δv を無関係な点 r_{k+1} まで
運ぶことになって不自然になる。

Δv の置き直しは別途1回要る。先端どうしを結んだ時点での始点は v_k の先端で
あって r_{k+1} ではないため。ただし移動先は目の前の共通始点なので、三角形の
一辺を頂点へ持ち帰るだけの自明な動きになる。

**速度も Δv も同じ倍率で拡大する**（相似）。Δv だけ伸ばすと三角形が閉じなく
なり、作図として嘘になる。倍率は全組で共通にしてある（`pairZoom()`）。組ごとに
変えると、組を送るたびに図が跳ねて読みにくい。

**注目中の組以外はすべて減光する。** 画面上の濃い矢印は常に2本だけ。これが
逐次方式の生命線で、画面が混むと別枠方式の問題がそのまま戻ってくる。

### ③④は実寸（倍率を掛けない）

②で描いた速度ベクトルをそのまま使う。こうすると v_{k+1} の先端がちょうど
次の黒点 r_{k+2} に乗り、前送りした v_k の先端は r_k を r_{k+1} について
折り返した点になる。両端が画面上の目印になるので、合っているかを確かめられる。

以前は「Δv を読める長さに」と倍率を掛けていたが、**長さの上限だけで頭打ちを
決めていて、矢印がどこから生えるかを見ていなかった**ので、斜方投射で画面の
上端を突き抜けた。`backScale()` が既に学んでいた教訓（見えている範囲で測る）を
また踏んだ形。実寸なら軌道から1ステップぶんしか外へ出ないので、はみ出さない。

折り返し点はその1ステップぶん外へ出るので、**③④のあいだだけ表示範囲を広げる**
（`pairViewCrop()`）。⑤で元のクロップに戻す。

Δv が短くなるのは素材の問題としてそのまま出す。短い＝向きの不確かさが大きい、
なので、矢印を伸ばすのではなく③のヒントでコマ間隔を広げるよう促す。
**⑤の一覧だけは `backScale()` で拡大したまま**（比較のための表示なので）。
④→⑤で一斉に伸びるところを 0.5 秒かけて見せる（`growDeltaV()`）。黙って
大きくなると別物に見える。

### アニメーションの速さ

既定はゆっくり（揃える 0.8 秒、置き直し 0.55 秒）。**Δv が着地したあと 0.3 秒の
間を置く**——この間が無いと「動いた→もう次」になって速すぎると感じる（実機で
指摘された）。「アニメを速く」のトグルを `localStorage` に覚えさせる。

実装上の注意：この間のあいだ `S.holding` を立てること。立てないと、自動モードの
駆動側が隙間を見て同じ組をもう一度描きにくる（実際に踏んだ）。

### ④はハンドル方式（スマホで決定的）

③が終わった時点で v_k の先端に**長さゼロの矢印とハンドル（つまむ輪）**を置き、
生徒はそれを動かして「決定」で確定する。一発のドラッグでは確定させない。

Δv の始点は生徒が選ぶものではなく、必ず v_k の先端に置かれる。そこを指で
正確に押さえさせるのは思考ではないのでアプリが引き受ける。**もう一方の先端が
どこかを見つけること**が④で観察したい思考なので、そこは手つかず（磁石なし）。

- **初期の矢印は長さゼロ。** 向きを持たせると答えを示唆する。とくに v_{k+1} の
  向きを初期値にしてはいけない——「加速度は速度の向き」という典型的な誤概念を
  アプリのほうから示唆することになる。
- **決定まで何度でも動かし直せる。** 指が先端を隠すので、拡大鏡を見ながら
  追い込む余地が要る。一発勝負だと拡大鏡が役に立たない。
- **掴む判定は単純に**——キャンバスのどこを触っても先端が動く。「ハンドルの
  近くだけ掴む」にすると指の太さで誤爆する。
- ドラッグ中は仮の矢印を別に出さず、ハンドルそのものを動かす。
- **④は正誤を判定しない。** 差し戻すのは「一度もハンドルに触れていない」ときだけ
  （`S.handleMoved`）。長さでは判定しない。ハンドルを始点に戻して Δv = 0 と
  答えたなら、それはその生徒の答えで、正しいかどうかは⑥が言う。そのぶん⑥で
  ゼロの回答を拾って「ゼロとしましたが、実際にはゼロではありませんでした」と
  返す（無評価で素通りさせない）。
- 拡大鏡は④のあいだ長押しを待たずに出す（`setEagerLoupe`）。長押しが要ると
  数ピクセルの追い込みには使えない。

### 一次元運動での表示（③④⑤共通）

台車・自由落下・バネでは v_k と v_{k+1} が同じ直線に乗る。手順は二次元と
まったく同じだが、表示だけ3点の手当てを入れた。

1. **2本が重なる。** 始点を揃えると同一直線上で入れ子になり（等加速度なら
   はみ出した先の部分がそのまま Δv）、1本に見える。色を分け、名札を付ける。
   **濃さだけで分けても引きの映像では溶ける**（最初そうして失敗した）。
   **平行にずらして逃げないこと。**ずらすと Δv が斜めになり、作図として嘘になる。

   運搬は「滑らせる」ではなく**持ち上げて運ぶ**。軌道と垂直に弧を描いて浮かせ、
   着地点で線の上に降ろす。自由落下では速度ベクトルが全部おなじ鉛直線に乗るので、
   線の上を滑らせると「どれが、どこから、どこまで」が読めない（実測で判明）。
   浮かせる量は、浮かせる向きに見えている範囲の 6%。高さを基準にすると、
   縦に細くクロップしているときに横へ振れて画面の外に出る。
   着地時のずれはゼロ（`amp * sin(π)`）なので、④の作図は何も嘘にならない。
   もとの場所の v_k は実体として濃いまま残す——出発点と運搬中のコピーが
   同時に見えていないと、どこからどこへ動いたのかが読めない。
2. **等速では作図が縮退する。** 2本が完全に重なって先端も一致し、Δv の長さが
   ゼロになる。エラーにせず、先端をその場でタップして決定すれば Δv = 0 の回答。

   「2本が重なっています」の案内を出す判定は、**点の間隔を基準**にする
   （Δv の中央値が点間隔の 3% 未満）。**ジッタで判定してはいけない**——
   ジッタは間隔1コマの二階差分から作られているが、等加速度運動ではその
   二階差分こそが信号なので、自由落下・斜面の台車・円運動まで
   「重なっている」と誤判定する（2回踏んだ）。
   判定は**画面上で先端が重なっているか**（拡大後の長さ）で行う。ジッタで判定
   してはいけない——ジッタの見積もりは間隔1コマの二階差分から作られているが、
   等加速度運動ではその二階差分こそが信号なので、自由落下やおもりで引いた台車を
   「重なっている」と誤判定する（実際に踏んだ）。
3. **⑤で Δv が軌道の上に乗る。** 二次元なら Δv は軌道の外へ出るが、一次元では
   黒点の列と同じ直線に並んで読めない。⑤⑥の一覧に限り、軌道と垂直にずらして
   並べる（比較のための表示であって作図ではないので嘘にならない）。
   ずらす向きは階段モードと同じ判定（主に縦の運動なら右、主に横なら下）。

### 一次元運動（自由落下）で分かったこと

実際の自由落下の動画（1920×1080、落下は幅45px・高さ934pxの縦帯）で測った結果と対策。

**1. 物体が小さすぎる。** スマホでは倍率 0.19 倍＝**直径27pxの物体が画面上5px**。
指で狙えない。原因は「余白がある」ことではなく、キャンバスが小さいこと。

**「軌道に合わせる」は、キャンバスの形も変えないと効かない。** キャンバスの縦横比を
動画に固定したままだと、縦に細い軌道では高さが先に詰まり、横の余白をいくら切っても
倍率は上がらない（1.09倍にしかならない）。クロップの縦横比に合わせてキャンバスを
縦長にすると、高さの予算を使い切れて**0.19 → 0.50 倍（物体 5px → 13.5px）**になった。
縦に細い範囲のときは、スマホでのキャンバス高さ上限も 42% → 60% に上げている。

細くしすぎると基準点を軌道の横に置けなくなるので、クロップの縦横比に下限
（`MIN_ASPECT = 0.38`）を設けて左右に余地を残す。

**2. 位置ベクトルと速度ベクトルが重なる。** 一次元では原理的に同じ直線に乗る。
拡大しても解決しない（重なりは向きの問題で、大きさの問題ではない）。
対策は基準点を軌道の**真横**に置くこと。補助として、②に進んだら①を薄くしている。

**3. 階段モードの矢印が画面の外に出ていた（不具合）。** 段を積む向きを
「平均速度に垂直」で決めていたため、自由落下では左向きになり、9本中3本が
座標マイナスになっていた。**段の向きは「主に縦の運動なら右、主に横の運動なら下」**に
変更し、配置・段差・倍率を表示範囲に収まるように計算し直した（範囲外 0 本を確認）。

**4. 階段の Δv が斜めに見える。** 段のずれは等間隔＝等時間なので、
**階段モードは v-t グラフ**である。そこで、
- 横軸に「→ 時間（1目盛り ◯ms）」とラベルと目盛りを描く
- 先端どうしを結んだ斜めの線は**補助線（灰色の細い破線）**にし、
  段差を引いた**本当の Δv を実線**で描く
- **段差スライダ**（0〜100%）で段差を 0 まで縮められる。0 にすると全集合と一致し、
  矢印が斜めから鉛直へ変形していくのが見える

発展（別枠）のあいだはクロップを一時的に解除する。抽象的な図なので、
軌道に合わせた細い範囲の中に描くと横幅が足りない。軌道へ戻ると元のクロップに戻る。
本筋の③④はストロボ画像の上で完結するので、クロップはそのまま効いている。

### 画面レイアウト

キャンバスを見ながら操作ボタンを押せることが要件。

- **スマホ**（〜899px）：キャンバスを画面上部に貼り付け（sticky）、操作はその下を
  スクロール。キャンバスの高さは画面の 42% までに制限（`js/ui/stage.js` の `fit()`）。
- **PC・タブレット**（900px〜）：左にキャンバスを固定し、右の列に操作を流す2カラム。

高さ制限でキャンバスの幅が余ることがあるので中央寄せにしてある。
ルーペの位置計算はその寄せ分を足している（`js/ui/loupe.js`）。

### 使うコマの選び方（つまみは「間隔」ひとつ）

以前は「開始コマ・間隔・個数」の3スライダで、**間隔 × 個数 = 使う時間の長さ**という
掛け算になっていた。間隔を1にしても点は増えず、同じ点数が狭い範囲に密集する。
実際に使ってもらって「直感に反する」と言われた設計なので、こう変えた。

- **つまみは「何コマおきに使うか」だけ。** 間隔を狭めると点が増え、広げると減る
- **使う範囲はトリムで決める。** 役割が分かれる
- `selection.count` は点数ではなく**上限**（区間が長いとき打ち切る）
- `selection.offset`（0〜interval-1）で開始をずらす。末尾の端数を前に出せる

**末尾の端数は捨てる。** 最後の1区間だけ短くすると Δt が不揃いになり、
その1点のために前後3本の Δv が壊れるため。捨てたことは
「余り◯コマは使いません」と必ず表示する（黙って切ると不具合に見える）。

**使うコマが変わったらストロボ画像を作り直す。** これが無いと、画像は生成時の
コマのままで「点を増やしてもプロットが増えない」ように見える（実際に踏んだ）。
背景の中央値推定は選択に依存しないので使い回し、選ばれたコマの取り込みだけ
やり直す（`HG.strobe.grabSelected`）。スライダから指を離したとき
（`selection:committed`）に走る。

### 手動打点の間隔

手動打点では、打ったコマの間隔がそのまま Δt になる。だから
**「打点したら◯コマ進む」の自動送りは便利機能ではなく、等間隔の保証**である。
UI にもそう書いてある。既定は2コマ（細かく打って、あとから間引く）。

粗く打ってしまった場合のために「**間を埋める**」を用意した。打点済みのコマの
中間コマへ順に連れて行くので、タップするだけで点が倍になる。撮り直しも
打ち直しも要らない。「間引くのは簡単だが増やすのは難しい」という非対称は、
これで解消する。

### 予測ステップ

**選択肢の文言と並び順は、集計アプリ側と完全に一致させること。** A/B/C/D の記号で
転記するので、片方だけ直すと集計が壊れる。定義は `js/presets/presets.js` の
`predictions` に集約してある。

斜方投射だけは「上昇中・頂点・下降中」を別々に3回聞く。1回だけ聞くと
「重力だから下」と知識で正解されてしまい、理解が確認できない。誤答が集中するのは頂点。
アプリ側は各点の速度から局面（上昇中／頂点／下降中）を判定し、**その局面で選んだ答えを
その点に重ねる**。合成動画で確認したところ、頂点だけが3問目の答えに割り当てられた。

集計・共有・サーバー送信は実装しない（別の集計アプリを使う）。役割は
「選ばせる・記号を見せる・⑥で重ねる」の3つだけ。

### 自動描写モード（提示・下見用）

手書きモードと同じパイプラインに `S.auto` というフラグを1つ立て、各ステップに入る
ときにそのステップぶんのデータを埋めるだけ。コードは二系統に分けていない。
自動モードの⑥は生徒の作図が無いので、**予測との突き合わせが主役**になる。

「結果まで一気に進む」（既定でオン）を付けてある。`runToEnd()` が手動の「次へ」を
自分で押していくだけなので、③の前送りも④の置き直しもそのまま通る。
授業で見せたときに「その矢印がどこから来たのか」が残る。**ステップを飛ばして
⑤だけ描く実装にはしない**——手書きモードと結果がずれる余地を作らないため。

手書きモードにも「残りの組を自動で」（`runRest()`）がある。手描きは最初の1〜2組
だけでよく、残りは同じアニメーションを高速で流す。**自動分だけ演出を変えない**
（一括表示にしない、アニメーションを省かない）。生徒が自分でやった操作がそのまま
速回しで続く、という連続性が要る。

実装上の注意：アニメーションの終了待ちで空回りするあいだは、暴走よけのカウンタを
減らしてはいけない（実際に踏んだ）。組送りになって必要な回数が点の数に比例する
ようになったので、カウンタも `12 + 4n` で取ってある。

#### 往復運動（単振り子・バネ）を自動描写モードで見せるとき

合成した単振り子（振れ角 25°、周期 60 コマ）で詰めた結果、**向きの精度は問題なく、
詰まるのは表示のほう**だった。3 つ直した。

**(1) 表示が軌道に合っていなかった**

自動描写モードでは誰も「軌道に合わせる」を押さないまま⑤まで行ってしまう。
振り子の弧は横に長く縦に薄い（振れ角 25°なら高さは弦の 1 割）ので、
素のままでは物体も矢印も数ピクセルにしかならない。作図開始時に自動で
`fitToTrack()` を掛けるようにした（2.0 倍）。

**(2) Δv の矢印が長すぎて互いに交差していた**

`backScale()` は「動画の横幅の 13%」で矢印の長さを決めていた。
弧の高さが 28px しかないところに 83px の矢印を描くので、隣どうしが重なって
どの点の矢印なのか読めない。上限を 2 つにして小さいほうを採る。

| 上限 | 理由 |
|---|---|
| 見えている範囲の 13% | クロップして拡大したとき、矢印だけが相対的に伸びるのを防ぐ |
| **隣り合う点の間隔の 1.3 倍** | これを超えると隣の矢印と交差する |

**(3) いちばん見せたい矢印だけが出ていなかった**

これが本質的な問題。Δv は前後の速度から作るので、**区間の両端には作れない**。
「端から端まで」きっちりトリムすると、折り返し点がちょうど区間の端に来て、
`速度ほぼゼロ・Δv 最大` というこのアプリの主題そのものの点が消える。

| トリム | 折り返しの点 |
|---|---|
| 端から端ぴったり | **無し**（区間の端なので Δv が作れない） |
| 端の少し外まで | 速さ 0.4px／\|Δv\| 25.6px（その区間で最大） |

そこで作図前に「折り返し点が区間のいちばん端にあります」と知らせ、
⑥のあとに「点◯は速さがほかの点の◯%しかないのに Δv は最も長いほうです」と出す。
後者は**結果なので⑤より前には出さない**（先に言うと予測が予測でなくなる）。

判定は「端が遅いか」だけでは足りない。自由落下も静止から始まるので最初の点が
いちばん遅いが、あれは折り返しではなく、手前へ伸ばしても手に持っている間の
a=0 が入るだけで意味が無い。**両端とも遅いか**で見分ける（往復を切り取ると
速さは真ん中で最大・両端で最小。自由落下は片側だけが遅い）。
振り子・バネのプリセットを選んでいるときは、片側だけでも知らせる。

あわせて、1 往復ぶん選んでいると行きと帰りの矢印が同じ位置に重なるので、
`revisits()` で通り直しを検出して知らせる（円運動にも効く）。

#### 自動描写モードでは、素材の粗さがそのまま矢印に出る

生徒が数本を吟味して描くぶんには問題にならないが、「撮ってすぐ向きを見る」使い方
では、ブレたコマの矢印が逆を向くと致命的になる（自由落下の実測で 8 本中 2 本）。
そこで作図パネルの自動モードに、いまの間隔での不確かさと
**「間隔を ◯ コマおきに広げる」**ボタンを出す。

対策として平滑化ではなく**間隔を広げる**方を採った。間隔を n 倍にすると Δv は n²倍に
なるのにジッタは変わらないので、2 倍に広げるだけで向きの精度は 4 倍になる。
平滑化でも似たことはできるが、衝突やばねのように加速度が急に変わる運動では
本物の変化まで鈍らせてしまう。

### スナップ（磁石）

| ステップ | スナップ | 吸着先 |
|---|---|---|
| 基準点の指定 | あり | 最寄りの黒点 |
| ① 位置ベクトル | あり | 黒点の中心 |
| ② 速度ベクトル | あり | 黒点の中心 |
| ③ 始点を揃える | ― | 自動 |
| ④ Δv | **なし** | ― |

④に磁石を掛けない。吸着先は「速度ベクトルの先端」になるが、自動で合わせると
先端を結ぶという操作の意味を考えずに済んでしまう。ここが観察したい思考の場所。

### 追跡の精度と、推奨間隔の決め方（実測）

既知の軌道（等加速度、真値 200 px/s²）の合成動画で確認した結果：

| コマ間隔 | 二階差分から求めた加速度 |
|---|---|
| 1 コマ | 0 px/s²（座標の丸めに埋もれる） |
| 3 コマ | 200.0 px/s² |
| 6 コマ | 200.0 px/s² |
| 10 コマ | 206.8 px/s² |

座標そのものの誤差は 0.3px 以下だが、加速度は二階差分なので、コマ間隔が狭いと
ジッタに埋もれ、広いと曲率のバイアスが乗る。

そこで推奨間隔は **4つの条件のいちばん厳しいもの**で決めている（`js/ui/selection.js`）。

1. コマ間の変位がジッタの 10 倍以上 … 速度が読めるための条件（開発プロンプトの目安）
2. Δv の向きの不確かさが 12° 以下 … 加速度の向きが読めるための条件（上の実測から追加）
3. **荒れるコマでも 20° 以下** … 矢印が逆を向かないための条件
4. **Δv が 5 本は残る範囲** … 広げれば精度は上がるが、矢印 2 本では授業にならない

#### 中央値だけでは足りない（実測で踏んだ）

当初ジッタは二階差分の**中央値**だけで見ていた。そのため自由落下の実測で「±9°」と
出ているのに、現場では矢印が 2 本逆を向いた。モーションブラーで重心が数コマだけ
15〜20px 飛んでいて、中央値はその外れ値を無視していたからである。
**矢印の向きを壊すのは典型値ではなく外れ値。**

そこで `jitterStats()` は 2 つ返す。

| | 出し方 | 使い道 |
|---|---|---|
| `typ` | 二階差分の中央値 ÷ 2 | 表示（ふだんのばらつき） |
| `high` | 二階差分の **90 パーセンタイル ÷ 2.4** | 推奨間隔を決めるのはこちら |

`high` を 2.4 で割るのは、二階差分そのものが既に √6σ ≒ 2.4σ 相当だから。
`angleUncertainty()` の中で 2.4 を掛け直したときに実寸（荒れるコマが Δv を
何 px ずらすか）に戻る。

合成動画で検証した結果（真値との角度差、`flips` = 逆を向いた本数）：

| 素材 | 1 コマおき | 推奨間隔 | 推奨での結果 |
|---|---|---|---|
| きれいな自由落下（σ=0.5px） | 逆向き 14/48 本 | 4 コマおき | 逆向き 0/11、最大 7° |
| ブレあり（8 コマに 1 回 15px 飛ぶ） | 逆向き 19/48 本 | 8 コマおき | 逆向き 0/5、最大 4° |
| ひどくブレる（5 コマに 1 回 20px） | 逆向き 18/48 本 | 8 コマおき | 逆向き 0/5、最大 33° |
| 加速度が小さい（a を 1/6 に） | 逆向き 23/48 本 | 8 コマおき | 逆向き 0/5、最大 22° |

ブラウザで通した結果（自動描写モードで最後まで、σ=0.6px）：

| 運動 | 推奨間隔 | 表示した見積もり | 実際のずれ |
|---|---|---|---|
| 等速円運動（真値＝中心方向） | 3 コマおき | ±9°（荒れるコマ ±10°） | 平均 1.9°、最大 3.4°、逆向き 0/18 |
| 自由落下（真値＝鉛直下向き） | 4 コマおき | ±9°（荒れるコマ ±13°） | 平均 5.0°、最大 14.7°、逆向き 0/13 |

`high` 側の見積もりは実測より悪めに出る（安全側）。そのぶん警告のしきい値は
甘めに取ってある（25° / 60°）。厳しくすると鳴りすぎる。

実際に表示するのは比ではなく **Δv の向きの不確かさ（度）** にした。Δv は二階差分なので、
座標の誤差 σ に対して Δv の誤差はおよそ √6σ ≒ 2.4σ、その横ずれが角度誤差 atan(2.4σ/|Δv|) になる。
⑥の判定が ±15° なので、この値がそれを超える間隔では判定そのものが成立しない。
合成動画（等加速度）で確かめたところ、推定 ±11° に対し実際の Δv の向きの散らばりは
79°〜105°（真値 90°）で、推定とよく合う。

条件2 がどの間隔でも満たせない運動＝加速度が小さい運動（台車の等速など）では、
間隔を無駄に広げず、代わりに区間全体へ点を散らす。このとき加速度プレビューは
矢印を描かず「Δv ≒ 0（ばらつき ±◯px）」と点で示す。**ノイズを引き伸ばして
それらしい矢印を出すと嘘になる。**

### iPhone で「この形式の動画を扱えません」と出た件（誤判定だった）

iPhone の Safari でスロー撮影の動画を読ませると
「この端末ではこの形式の動画を画像として扱えません（HEVC/H.265 の可能性）」
で止まる、という報告。調べたら**動画は正常に読めていて、判定のほうが壊れていた**。

旧 `testDraw()` は「先頭 0.1 秒の**左上 64×64** の画素の合計が 0 なら失敗」。
これが誤判定する理由は3つ。

| 原因 | 何が起きるか |
|---|---|
| 左上の隅しか見ていない | 暗い壁・天井・レターボックスの黒帯で合計 0 |
| 1か所しか見ていない | iPhone の動画は露出が決まるまで先頭が暗い |
| シーク直後に描いている | iOS は seeked の時点でまだコマを用意しておらず黒が返る |

合成動画で再現した（`先頭が黒・左上も暗い`）：**旧＝draw（誤判定）／新＝ok**。

直したのは4か所。

1. **全体を縮小して見る**（左上 64×64 → 全面を 48×48 に縮小）
2. **3か所で見る**（10% / 35% / 60%。どれか1つでも通れば ok）
3. **コマが提示されるまで待つ**（`requestVideoFrameCallback`。無ければ rAF 2回）
4. **下地を敷いてから重ねる** — 検査キャンバスを先にマゼンタで塗ってから
   `drawImage` する。下地が残っていれば「1枚も描けていない」、消えていれば
   「描けたが黒い場面だった」。この2つは原因も対処も違うので、
   戻り値を `'draw'` と `'black'` に分けた。

`seekTo()` にもバグがあった。タイムアウトで `res()` するだけで `seeked` の
リスナを外していなかったため、大きなファイルでタイムアウトが先に来ると
**シーク途中のコマを描いて真っ黒になっていた**。判定時は 8 秒まで待つ。

あわせてスロー撮影対策：
- `preload` を `'auto'` → `'metadata'`（数百 MB を抱え込んでタブが落ちるのを防ぐ）
- メタデータ待ちを 20 秒 → 60 秒
- ハンドラを付けてから `src` を入れる（速い素材で `loadedmetadata` を取りこぼしていた）
- 間隔スライダの上限を固定 30 →**区間 ÷ 6**（最大 120）。
  240fps・1200 コマの素材で、いちばん粗くしても点が密すぎた。
  1200 コマで推奨 25 コマおき＝点の間隔 104 ms になる。

エラー文も書き直した。旧文面は「撮影した端末で開いてください」だったが、
撮影した端末（iPhone）で開いている人には打つ手が無い。
いまは何を調べてどうだったか（`0.30s:明るさ0/下地0%` など）を必ず添える。
